## Context

Проект новый. Пользователь хранит десятки тысяч фото и видео на нескольких дисках Windows, в разных форматах (JPEG, PNG, HEIC, RAW, MP4/MOV и др.). Приложение работает локально на том же ПК, файлы читаются напрямую с дисков. Стек: Python, FastAPI, Pillow, SQLite. Группировка только по датам, дубли только точные (SHA-256), распознавания лиц, событий и персонажей нет. Файлы перемещаются, а не копируются, поэтому целостность данных важнее скорости.

## Goals / Non-Goals

**Goals:**
- Найти медиафайлы на выбранных дисках и составить каталог в SQLite.
- Надёжно определить дату съёмки и хранить источник даты.
- Найти точные дубли и безопасно убрать лишние копии.
- Переместить файлы в `ГГГГ/ММ/ДД` без потери данных, с журналом и откатом.
- Отдельно конвертировать HEIC в JPEG, сохранив метаданные.
- Дать удобный web-интерфейс с прогрессом длительных операций.

**Non-Goals:**
- События, персонажи, распознавание лиц.
- Поиск похожих (не идентичных) изображений, перцептивные хеши.
- Многопользовательский режим, аутентификация, доступ из сети.
- Облачная синхронизация.

## Decisions

### Архитектура: один локальный процесс
FastAPI-сервер на `127.0.0.1` отдаёт REST API и статический фронтенд. Тяжёлые операции идут в фоновых задачах внутри того же процесса. Браузер сам не имеет доступа к дискам, поэтому весь файловый ввод-вывод делает бэкенд.
- Альтернатива: десктопное приложение (Electron, Tk). Отклонено: требование «в web», а backend всё равно нужен.

### Фоновые задачи с прогрессом
Сканирование, хеширование, конвертация и перемещение выполняются как задачи (таблица `jobs` в SQLite: статус, обработано байт и файлов, ошибка). Исполнение через пул потоков (`ThreadPoolExecutor`), так как работа упирается в диск и в библиотеки, освобождающие GIL. Прогресс отдаётся через SSE (`/api/jobs/{id}/events`), отмена через флаг, который задача проверяет между файлами и между блоками при хешировании.
- Альтернатива: Celery или RQ. Отклонено: избыточно для локального приложения.
- Прогресс считается по байтам, а не по числу файлов, из-за больших видео.

### Модель данных SQLite
- `roots(id, path, volume_id, label, last_scan)`: корни сканирования; диск определяется по volume serial number, а не по букве.
- `files(id, root_id, rel_path, size, mtime_ns, sha256, kind, status, taken_at, date_source, date_confidence, group_key)`. `status`: `present`, `missing`, `quarantined`, `moved`. `group_key` связывает RAW+JPEG и Live Photo.
- `derived_files(file_id, source_file_id, op)`: связь конвертированного файла с оригиналом.
- `dup_groups(id, sha256)` и `dup_members(group_id, file_id, is_keeper)`.
- `operations(id, plan_id, kind, src, dst, sha256, status, ts)`: журнал перемещений, карантина и конвертаций.
- `jobs(...)`.
Ручные правки даты хранятся в отдельной колонке (`manual_taken_at`) и не затираются при повторном скане.
- Доступ через стандартный `sqlite3` с WAL-режимом; отдельная ORM не нужна.

### Дата съёмки: каскад источников
1. EXIF `DateTimeOriginal` (фото) или `creation_time` контейнера (видео, через `ffprobe`).
2. Дата в имени файла по набору регулярных выражений (`IMG_YYYYMMDD_…`, `PXL_…`, `WhatsApp …`).
3. `mtime` файла с пониженной уверенностью.
4. Иначе «дата неизвестна»: файл попадает в `_без даты/`.
Хранится источник и уверенность. EXIF-время считается локальным и не пересчитывается. Ручная дата имеет наивысший приоритет.

### Поиск дублей: двухэтапный SHA-256
Сначала файлы группируются по размеру; SHA-256 считается только для файлов, у которых размер совпал с другим. Хеширование потоковое, блоками (например, 1 МиБ). Хеш кэшируется по паре `(size, mtime_ns)` и пересчитывается только при её изменении. Правило выбора оригинала по умолчанию: файл, уже лежащий в целевой структуре `ГГГГ/ММ/ДД`; при равенстве — самый короткий путь, затем самый ранний `mtime`. Пользователь может выбрать оригинал вручную.
- Лишние копии не удаляются сразу, а переносятся в карантин (`_duplicates` в корне назначения) с записью в журнал.

### Перемещение: план, проверка, журнал
Процесс: построить план (`src → dst` по шаблону `{YYYY}/{MM}/{DD}`), показать предпросмотр (число файлов, объём, конфликты, нехватка места), выполнить после подтверждения.
- Тот же том: атомарный `os.replace`.
- Другой том: копирование, сверка SHA-256 копии с исходным хешем, только затем удаление оригинала.
- Каждая операция пишется в журнал до и после выполнения; после сбоя прерванная операция определяется по журналу и безопасно доводится или откатывается.
- Конфликт имён: если в целевой папке есть файл с другим хешем, к имени добавляется суффикс `_1`, `_2`; если хеш совпал, файл считается дублем и уходит в карантин.
- Связанные файлы (`group_key`) перемещаются вместе; папка определяется по дате основного файла группы.
- Шаблон пути и «граница дня» (по умолчанию 00:00) вынесены в настройки.
- Откат: по журналу выполняется обратное перемещение, если файл на новом месте не изменялся.

### Конвертация HEIC → JPEG
`pillow-heif` регистрируется в Pillow, файл читается, применяется ориентация к пикселям, поэтому тег ориентации в результате сбрасывается (нет двойного поворота). EXIF и ICC-профиль переносятся явно, качество JPEG задаётся настройкой (по умолчанию 92). Результат кладётся рядом с оригиналом, конфликт имён решается суффиксом. Связь записывается в `derived_files`, чтобы производный файл не считался новым фото и не участвовал в поиске дублей как самостоятельное изображение. Оригинал по умолчанию сохраняется; удаление оригинала (в карантин) выполняется отдельным шагом.
- Live Photo: конвертируется только HEIC, парный MOV остаётся на месте.
- Альтернатива: PNG. Отклонено как формат по умолчанию: файлы в разы больше, для фото без прозрачности выигрыша нет.

### Форматы и видео
Поддерживаемые расширения задаются конфигурацией. Фото: JPEG, PNG, WebP, HEIC, TIFF, RAW (метаданные и встроенное превью). Видео: MP4, MOV, MKV, AVI и др. Метаданные и миниатюры видео получаются через `ffprobe`/`ffmpeg`. При отсутствии `ffprobe` приложение продолжает работать: дата видео определяется по имени файла или `mtime`, миниатюры заменяются заглушкой, в интерфейсе показывается предупреждение. Неподдерживаемые файлы игнорируются, но их число показывается в отчёте о сканировании.

### Web-интерфейс
Одностраничный фронтенд без сборки (статические файлы, лёгкий JS), обращающийся к REST API. Основные экраны: источники, лента каталога по датам с фильтрами, дубли, предпросмотр и выполнение перемещения, конвертация HEIC, журнал операций. Миниатюры генерируются лениво и кэшируются на диске.
- Альтернатива: SPA на React со сборкой. Отклонено на старте: усложняет установку, ценности для локального инструмента мало.

## Risks / Trade-offs

- [Потеря файлов при перемещении между дисками] → копирование, сверка SHA-256 и лишь затем удаление; журнал и откат; предпросмотр плана.
- [Неверная дата отправит файл не в ту папку] → хранение источника и уверенности, отдельная папка `_без даты/`, ручная правка даты до перемещения.
- [Расхождение UTC и локального времени у видео] → явная настройка политики времени видео; по умолчанию `creation_time` считается локальным временем, если пояс не указан.
- [Долгое первое хеширование десятков ГБ видео] → двухэтапный поиск дублей, кэш хеша, прогресс по байтам, возможность отмены и продолжения.
- [Смена буквы диска ломает пути] → идентификация корня по volume ID, путь хранится относительно корня.
- [Потеря метаданных при конвертации HEIC] → явный перенос EXIF и ICC, тест на сохранность даты.
- [Отсутствие ffprobe] → деградация функциональности с предупреждением, приложение остаётся рабочим.
- [Файл изменён вне приложения между планом и выполнением] → перед операцией сверяются размер и mtime; при расхождении файл пропускается и попадает в отчёт.

## Open Questions

- Политика часового пояса для видео: оставить «creation_time как локальное» или переводить UTC в пояс машины?
- Как доставлять `ffmpeg`/`ffprobe`: требовать установки пользователем или класть рядом с приложением?
- Нужна ли настраиваемая граница дня (например, 04:00) в первой версии или достаточно 00:00?
- Удалять ли пустые исходные папки после перемещения: автоматически или по кнопке?
- Единый корень назначения для всех перемещений или отдельный на каждый запуск?
- Нужна ли в будущем конвертация других форматов (RAW, MOV → MP4): проектировать конвертер как общий интерфейс с HEIC в качестве первой реализации?
